# 话题发布订阅机制设计评估

## 1. 结论

当前工程适合先建立一套轻量的“最新状态主题”机制：每个主题使用一个长度为 1 的 FreeRTOS Queue，生产者调用 `xQueueOverwrite()` 发布完整快照，消费者调用 `xQueuePeek()` 获取最新快照而不移除数据。

推荐结论如下：

- MPU6050、AS5600、系统状态、电机反馈等“只关心最新状态”的数据，适合使用 `Overwrite + Peek`。
- 每个主题只允许一个逻辑生产者，可以有多个消费者。
- Queue 保存完整结构体副本，不传播生产者内部对象的指针。
- 每个样本携带 `sequence` 和 `timestamp_ms`，消费者据此判断新旧、丢帧和数据过期。
- 普通消费者按自己的周期 `Peek` 即可，例如传感器 200 Hz 发布、UART 10 Hz 读取。
- 需要收到新数据后立即运行的消费者，应在主题之外叠加任务通知；通知只负责唤醒，Queue 仍负责保存数据。
- 命令、按键边沿、故障事件等“每一条都不能静默丢失”的数据不能使用 Overwrite，应使用普通多槽 Queue。
- FOC 高频中断不应在每次控制周期中反复复制完整 Queue 项；应采用降频发布、任务侧缓存或专门的双缓冲/序列锁方案。

第一阶段不建议实现动态主题注册、字符串主题名、运行时类型识别或动态内存订阅。这些机制对当前 STM32F407 工程增加的复杂度明显大于收益。

## 2. 设计目标

话题层要解决的核心问题不是“把全局变量换一个名字”，而是建立明确的数据所有权和访问方向。

### 2.1 生产者边界

生产者负责：

- 访问硬件并完成原始数据处理。
- 生成一个内部一致的完整样本。
- 更新 `sequence` 和 `timestamp_ms`。
- 将完整样本发布到对应主题。
- 在采样失败时保留旧主题数据，不发布半成品。

生产者不负责：

- UART 格式化和发送。
- 决定姿态融合、记录器或控制器的消费周期。
- 等待所有消费者处理完当前样本。
- 为慢消费者保存无限历史。

### 2.2 消费者边界

消费者负责：

- 从主题复制最新快照到自己的局部变量。
- 用 `sequence` 判断是否出现新样本或跳过样本。
- 用 `timestamp_ms` 判断数据是否过期。
- 按自身周期完成 UART、融合、记录或控制。

消费者不能：

- 修改主题内的数据。
- 直接访问生产者对象，例如直接持有 `mpu6050 &`。
- 通过读取操作清空所有其他消费者需要的数据。
- 假定自己一定能处理每一个状态样本。

## 3. 当前工程为什么适合单槽最新值主题

当前两个传感器任务均以 5 ms 周期运行，也就是约 200 Hz；UART 输出周期为 100 ms，也就是 10 Hz。

如果 UART 消费者使用普通 FIFO Queue，并要求保存所有 MPU6050 数据，那么每 100 ms 会积累约 20 帧。UART 实际只需要最新姿态，处理全部旧帧没有价值，还会浪费 RAM 和发送时间。

使用单槽主题时：

```text
MPU6050 生产任务：200 Hz ──Overwrite──▶ MPU6050 最新值主题
                                              ├──Peek──▶ UART：10 Hz
                                              ├──Peek──▶ 姿态融合：100 Hz
                                              └──Peek──▶ 状态监控：1 Hz

AS5600 生产任务：200 Hz ───Overwrite──▶ AS5600 最新值主题
                                              ├──Peek──▶ UART：10 Hz
                                              ├──Peek──▶ 电机控制桥接任务
                                              └──Peek──▶ 数据记录任务
```

慢消费者自然跳过中间状态，但总能得到最近一次完整快照。不同消费者不会因为另一个消费者读取了数据而失去访问机会。

当前样本负载大小约为：

| 主题 | 当前样本结构体大小 | 200 Hz 复制量 |
|---|---:|---:|
| `mpu6050_sample` | 48 字节 | 约 9.6 KB/s |
| `as5600_sample` | 24 字节 | 约 4.8 KB/s |

这个复制量对 STM32F407 很小。每个主题只保存一个样本，RAM 成本也是固定的。

## 4. Overwrite 和 Peek 的准确语义

### 4.1 `xQueueOverwrite()`

`xQueueOverwrite()` 只应与长度为 1 的 Queue 配合使用：

- Queue 为空时，写入第一个样本。
- Queue 已满时，直接用新样本覆盖旧样本。
- 数据按 Queue 创建时指定的大小复制，不是保存传入指针。
- 任务版本不能在 ISR 中调用。
- 对长度大于 1 的 Queue 使用 Overwrite 不符合该 API 的设计用途。

因此它表达的是“最新状态邮箱”，不是“历史消息队列”。

### 4.2 `xQueuePeek()`

`xQueuePeek()` 将当前 Queue 项复制到消费者缓冲区，但不会把它移除：

- 多个消费者可以先后读取同一份最新快照。
- 生产者下一次 Overwrite 前，重复 Peek 会得到同一个样本。
- 消费者必须通过 `sequence` 判断样本是否真的更新。
- Queue 尚未收到第一帧时，零等待 Peek 会返回失败。

一个容易踩坑的点是：

> `xQueuePeek(queue, &sample, portMAX_DELAY)` 只能可靠表达“等待主题首次出现数据”，不能表达“等待下一帧新数据”。

第一次发布后 Queue 将始终保持非空，后续阻塞式 Peek 会立即返回旧快照，可能造成任务空转。等待“下一次发布”必须使用任务通知、信号量或显式轮询周期。

### 4.3 为什么消费者不能使用 `xQueueReceive()`

`xQueueReceive()` 会移除 Queue 项。如果多个消费者共享同一个单槽 Queue，那么先 Receive 的消费者会让其他消费者看到空 Queue，这与广播主题语义冲突。

最新状态主题应统一使用 Peek。只有真正需要竞争消费、每条消息只交给一个处理者时才使用 Receive。

## 5. 推荐的软件分层

当前采用下面的目录结构，不为每个设备额外增加话题文件：

```text
user_lib/
├── drivers/
│   ├── mpu6050.h/.cpp
│   └── as5600.h/.cpp
├── system/
│   ├── topic.h
│   └── start.cpp
├── devices/
│   ├── mpu6050_dev.h/.cpp
│   └── as5600_dev.h/.cpp
└── debug/
    └── sensor_debug.h/.cpp
```

职责划分：

| 层 | 职责 | 不应承担的职责 |
|---|---|---|
| `drivers` | 设备寄存器访问、物理量换算、维护驱动内部状态 | UART、主题订阅、业务任务管理 |
| `system/topic.h` | 提供静态最新值和 FIFO 通用模板 | 定义具体业务主题或访问硬件 |
| 传感器 `devices` | 保存具体话题、创建采样任务、调用驱动并发布样本 | 直接服务某个特定消费者 |
| `debug` | Peek 设备最新样本并完成 UART 调试输出 | 修改生产者和话题内部状态 |
| `system/start.cpp` | 初始化主题并创建各任务 | 处理具体采样或消费逻辑 |

这样可以把当前“传感器采样和 UART 打印写在同一个任务中”的耦合拆开。关闭 UART 遥测不会影响传感器继续生产数据，增加新的消费者也不需要修改驱动。

## 6. 推荐 API 草案

当前已经在 [`topic.h`](../user_lib/system/topic.h) 中提供两个通用静态模板：

- `topic::latest_topic<item_type>`：长度固定为 1，提供 Overwrite/Peek 语义。
- `topic::fifo_topic<item_type, QUEUE_LENGTH>`：编译期指定容量，提供 Send/Receive FIFO 语义。

具体传感器设备直接在自己的 `.cpp` 中创建模板静态实例，并通过设备头文件只开放读取接口。这样不需要额外的 `topics` 目录，同时仍能隐藏发布权限和具体 Queue 类型。

### 6.1 设备头文件

以 MPU6050 为例：

```cpp
#ifndef MPU6050_DEV_H
#define MPU6050_DEV_H

#include "drivers/mpu6050.h"

namespace mpu6050_dev
{
    bool peek_latest(mpu6050_sample &sample);
    bool init();
}

#endif
```

接口约定：

- `peek_latest()` 可供任意任务消费者调用，不阻塞。
- `init()` 初始化话题并创建生产任务。
- `publish()` 不作为公共 API，生产任务直接操作 `.cpp` 内的私有话题实例。
- Queue 句柄不暴露给外部，防止消费者绕过约定调用 Receive 或 Reset。

消费者只需包含 `devices/mpu6050_dev.h`。由于发布能力只存在于 `mpu6050_dev.cpp`，其他模块无法通过公共接口冒充生产者。

### 6.2 设备内的话题实现

```cpp
#include "mpu6050_dev.h"

#include "system/topic.h"

static topic::latest_topic<mpu6050_sample> sample_topic;

/**
 * @brief 读取最新 MPU6050 样本但不移除主题数据
 *
 * @param sample 用于接收快照的对象
 *
 * @return 已经存在有效样本时返回 true
 */
bool mpu6050_dev::peek_latest(mpu6050_sample &sample)
{
    return sample_topic.peek(sample);
}

/**
 * @brief 初始化 MPU6050 设备、话题并创建生产任务
 */
void mpu6050_dev::init()
{
    if(!sample_topic.init())
    {
        Error_Handler();
    }

    // 随后创建 MPU6050 生产任务。
}
```

`latest_topic` 内部使用 `xQueueCreateStatic()`，不会占用 FreeRTOS heap。当前工程已经启用 `configSUPPORT_STATIC_ALLOCATION=1`。

### 6.3 生产任务

生产任务只负责采样和发布：

```cpp
while(true)
{
    i2c_result result = imu.update();

    if(result == i2c_result::OK)
    {
        sample_topic.publish(imu.sample());
    }

    vTaskDelayUntil(&last_wake_time,
        pdMS_TO_TICKS(MPU6050_UPDATE_PERIOD_MS));
}
```

`publish()` 内部会立即复制完整结构体，因此传入 `imu.sample()` 返回的引用是安全的。主题中不保存该引用。

读取或处理失败时不发布新数据。消费者会观察到 `sequence` 停止变化，并可以通过时间戳判断数据已经过期。

### 6.4 周期消费者

UART 消费者可以用自己的 100 ms 周期读取最新值：

```cpp
static uint32_t previous_sequence = 0U;

mpu6050_sample sample{};
if(mpu6050_dev::peek_latest(sample) &&
    sample.sequence != previous_sequence)
{
    send_mpu6050_telemetry(sample);
    previous_sequence = sample.sequence;
}
```

如果生产者在两个 UART 周期之间发布了 20 次，消费者只处理第 20 次。可以用无符号减法统计跳过的样本：

```cpp
uint32_t sequence_delta = sample.sequence - previous_sequence;
uint32_t skipped_samples = sequence_delta > 0U ? sequence_delta - 1U : 0U;
```

该写法在 `uint32_t` 自然回绕时仍能工作，前提是两次消费之间不跨越超过半个计数范围。

## 7. 时间戳和有效性

当前主题样本使用：

```cpp
uint32_t sequence;
uint32_t timestamp_ms;
```

推荐约定：

- `sequence=0` 表示尚未发布过完整样本。
- 第一个成功样本使用 `sequence=1`。
- 只有完整采样成功后才同时更新 `sequence` 和 `timestamp_ms`。
- `timestamp_ms` 表示样本采集和处理完成的系统时间，不表示消费者读取时间。
- 消费者使用无符号时间差处理约 49.7 天一次的毫秒计数回绕。

过期判断示例：

```cpp
uint32_t now_ms = (uint32_t)xTaskGetTickCount() *
    (uint32_t)portTICK_PERIOD_MS;
uint32_t age_ms = now_ms - sample.timestamp_ms;

if(age_ms > MPU6050_STALE_TIMEOUT_MS)
{
    enter_sensor_stale_state();
}
```

不要仅凭 Queue 中存在数据就认为传感器当前健康。单槽 Queue 会一直保留最后一次成功样本，因此 `timestamp_ms` 是判断断线和采样停滞的必要信息。

如果业务还需要区分 NACK、超时和初始化失败，建议单独增加低频健康状态主题：

```cpp
struct sensor_health
{
    uint32_t sequence = 0U;
    uint32_t timestamp_ms = 0U;
    uint32_t error_count = 0U;
    i2c_result last_error = i2c_result::OK;
    bool ready = false;
};
```

不要为了传递错误而发布内容不完整的传感器样本。

## 8. 多消费者和订阅语义

### 8.1 轮询式订阅

对于当前工程，优先推荐轮询式订阅：

- 生产者只执行 Overwrite。
- 每个消费者按自己的固定周期 Peek。
- 每个消费者保存自己的 `previous_sequence`。
- 消费者之间完全独立。

它没有真正的“订阅者注册表”，但数据边界、广播语义和多消费者能力已经具备，代码与运行时成本最低。

### 8.2 事件驱动订阅

如果某个任务必须在发布后立即被唤醒，可以在主题内维护固定容量的订阅任务表：

```text
publish(sample)
    ├── xQueueOverwrite(topic_queue, &sample)
    ├── xTaskNotifyGive(subscriber_0)
    ├── xTaskNotifyGive(subscriber_1)
    └── xTaskNotifyGive(subscriber_2)
```

消费者流程：

```cpp
while(true)
{
    ulTaskNotifyTake(pdTRUE, portMAX_DELAY);

    mpu6050_sample sample{};
    if(mpu6050_dev::peek_latest(sample))
    {
        process_sample(sample);
    }
}
```

注意事项：

- 任务通知可能合并多次发布，不能用通知次数代替样本序号。
- 被唤醒后仍应 Peek Queue，Queue 才是数据真值来源。
- 每个任务默认只有一组通知状态；使用前要明确该通知槽由话题系统拥有，避免与其他模块冲突。
- 订阅者表应使用固定数组和固定上限，不建议运行时动态分配节点。
- 发布动作必须先 Overwrite，再通知，保证任务醒来时数据已经可读。
- 任务删除前必须取消订阅，否则主题会保留失效的 `TaskHandle_t`。

当前工程的任务通知功能默认启用，因此技术上可以实现。但 MPU6050 和 AS5600 的 UART 消费并不需要立即响应，第一阶段没有必要加入订阅表。

### 8.3 为什么不推荐 Queue Set

Queue Set 适合等待多个 Queue/信号量中的任意一个变为可读。单槽 Peek 主题第一次发布后会永久保持非空，因此它会持续表现为“可读”，不能自然表达“又发布了一帧”。

如果一个消费者要等待多个主题的新数据，推荐：

- 用任务通知位表示哪些主题有更新；或
- 用 Event Group 唤醒，再分别 Peek 各主题；或
- 采用固定周期读取，并检查各自 `sequence`。

## 9. 数据类型分类

建立话题机制前必须区分状态和事件：

| 数据类型 | 示例 | 推荐机制 | 是否允许覆盖 |
|---|---|---|---|
| 最新状态 | 姿态、编码器角度、电压、温度 | 单槽 Queue + Overwrite/Peek | 是 |
| 控制设定值 | 最新目标角度、最新目标速度 | 单槽 Queue + Overwrite/Peek | 通常是 |
| 离散事件 | 故障发生、按键边沿、模式切换请求 | 多槽 Queue + Send/Receive | 否 |
| 命令事务 | 参数写入、校准请求、应答 | 请求 Queue，必要时配应答通知 | 否 |
| 字节流 | UART RX、连续协议字节 | StreamBuffer | 由容量策略决定 |
| 有边界消息 | 一帧变长协议数据 | MessageBuffer 或消息 Queue | 由容量策略决定 |
| 高频硬实时快照 | FOC ISR 内部状态 | 双缓冲、序列锁或降频 Queue | 只保留最新值 |

如果把故障事件放入单槽 Overwrite 主题，连续发生的多个故障可能只剩最后一个；如果把 200 Hz 姿态放入可靠 FIFO，又会无意义地堆积旧状态。两类数据不能使用同一种交付语义。

## 10. ISR 和 FOC 路径评估

### 10.1 ISR 可用 API

FreeRTOS 提供：

- `xQueueOverwriteFromISR()`：在 ISR 中发布单槽最新值。
- `xQueuePeekFromISR()`：在 ISR 中复制当前最新值，不移除。

调用这些 API 的中断优先级必须满足 FreeRTOS 约束。当前工程：

- `configLIBRARY_MAX_SYSCALL_INTERRUPT_PRIORITY = 5`
- TIM1 Update IRQ 数字优先级为 5
- TIM8 Update IRQ 数字优先级为 5

因此当前 TIM1/TIM8 中断处在允许调用 FreeRTOS `FromISR` API 的边界上。以后若把 FOC IRQ 调到数字优先级 0～4，就不能再从该中断调用这些 API。

### 10.2 不建议每个 FOC 周期 Peek Queue

即使 API 合法，也不表示它适合高频控制路径。每次 Peek 都会：

- 进入 FreeRTOS Queue 临界区。
- 复制完整结构体。
- 增加控制周期执行时间和抖动。

例如 FOC 以 20 kHz 运行，而 AS5600 只以 200 Hz 更新，那么连续 100 次控制中断读到的都是同一帧。每次中断执行 Queue Peek 没有收益。

推荐方案：

1. AS5600 任务以 200 Hz 发布主题。
2. 一个普通任务在主题更新后复制数据到控制侧缓存。
3. FOC ISR 只读取已经准备好的固定大小控制缓存。
4. ISR 用 `sequence` 或 `timestamp_ms` 检查缓存是否更新、是否过期。

如果任务与 ISR 共享的结构体超过处理器天然原子宽度，控制缓存需要双缓冲或序列锁，不能直接依赖普通结构体赋值恰好不被打断。

### 10.3 ISR 作为生产者

FOC ISR 如果要发布遥测状态，建议先降频，例如每 100 次控制循环发布一次，再调用 `xQueueOverwriteFromISR()`。不要在 20 kHz 中断中每次复制大结构体并唤醒日志任务。

ISR 发布时要正确处理：

```cpp
BaseType_t higher_priority_task_woken = pdFALSE;
xQueueOverwriteFromISR(topic_queue,
    &sample,
    &higher_priority_task_woken);
portYIELD_FROM_ISR(higher_priority_task_woken);
```

## 11. 方案对比

| 方案 | 多消费者 | 快照一致性 | 可等待新数据 | RAM/复杂度 | 适用结论 |
|---|---|---|---|---|---|
| 裸全局结构体 | 可以 | 需要自行同步 | 否 | 最低 | 边界弱，不推荐作为公共机制 |
| Mutex + 全局结构体 | 可以 | 可以 | 否 | 低 | 任务可用，但 ISR 不方便 |
| 单槽 Queue + Overwrite/Peek | 可以 | 可以 | 仅首次数据；后续需轮询/通知 | 低 | 当前状态主题首选 |
| 每个订阅者一个 Queue | 可以 | 可以 | 可以 | 随订阅者数量增长 | 每个消费者都必须接收每条消息时使用 |
| 多槽事件 Queue | 竞争消费或单消费者 | 可以 | 可以 | 中等 | 离散事件和命令首选 |
| StreamBuffer/MessageBuffer | 通常按单读者设计 | 取决于协议 | 可以 | 中等 | 字节流或变长帧，不适合广播快照 |
| 双缓冲/序列锁 | 可以 | 需正确实现 | 通常配通知 | 中等偏高 | 高频 ISR 与任务共享快照 |

## 12. 推荐实施顺序

### 第一阶段：静态最新值主题

1. 新建 `user_lib/topics`。
2. 为 MPU6050 和 AS5600 各创建一个长度为 1 的静态 Queue。
3. 在 `start_init_all()` 中先初始化主题，再创建任务。
4. 传感器任务只负责 `update()` 和 `publish()`。
5. 新建统一 UART 遥测任务，以 10 Hz Peek 两个主题。
6. 用 `sequence` 避免重复处理，用 `timestamp_ms` 判断过期。

这一阶段已经能建立明确的生产者/消费者边界，且几乎不改变硬件驱动。

### 第二阶段：健康状态和统计

1. 为传感器增加健康状态主题。
2. 记录连续错误数、最后错误和最后成功时间。
3. 在 UART 或调试界面输出丢帧、过期和错误统计。

### 第三阶段：按需增加唤醒机制

只有消费者确实需要低延迟响应时，再增加固定订阅表和任务通知。周期遥测、状态面板等消费者继续轮询，不需要统一强制事件驱动。

### 第四阶段：FOC 专用数据通道

根据实际 FOC 频率和延迟预算测量 Queue 复制开销，再决定采用：

- 降频 `OverwriteFromISR()`；
- 任务到 ISR 的双缓冲；
- 序列锁保护的最新快照。

不要在没有测量控制周期抖动前，把通用话题 API 直接放进最高频的 FOC ISR。

## 13. 最终建议

当前工程最合适的落地方案不是完整消息总线，而是“强类型、静态分配、单生产者、多消费者”的最新值主题层：

```text
驱动对象 → 生产任务 → 单槽最新值主题 → 周期消费者
                                      └→ 按需通知的实时消费者
```

建议坚持以下规则：

1. 一个主题只表达一种稳定数据结构。
2. 一个主题只有一个逻辑生产者。
3. 状态主题只用 Overwrite/Peek，不使用 Receive。
4. Queue 中保存值，不保存生产者内部对象指针。
5. `sequence` 用于判断更新和跳帧。
6. `timestamp_ms` 用于判断新鲜度和断流。
7. 通知是唤醒手段，不是数据存储。
8. 事件和命令使用可靠 FIFO，不使用 Overwrite。
9. 驱动层不知道 UART、订阅者和业务逻辑。
10. FOC 高频 ISR 使用专门评估过的轻量快照通道。

按这个方向演进，可以先以很低成本解耦当前传感器与 UART，后续增加姿态融合、电机控制、记录器和调试界面时也不需要反复修改底层驱动。
